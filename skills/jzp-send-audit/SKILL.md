## 🔴 四个已知陷阱

### 1. 队列文件名不能用来判「首封 vs 跟进」
`发信队列.json`（主队列）里**混着 21 封 `Re:` 跟进信**（batch6 = 首封 23 + 跟进 21 = 44）。
**正确做法**：按收件人分组 → 按时间排序 → 第 1 封才是首封。

### 2. 收件箱退信数 > 黑名单地址数
**同一封退信可同时报多个失败地址**（如 `{{COMPANY_DOMAIN}}` 的 9/23 退信含 `jchamblee@`+`walt@`）。
`扫描退信.py` 已正确处理，**不要以为漏了**。

### 3. 「自动回复」≠ 回复，但是好消息
`Automatic reply:` 开头的不是意向，但**证明地址有效、邮件已送达**。统计时要单列。
⚠️ 但 `扫描回复.py` 的 `SKIP_SUBJECT` **会把自动回复整条丢弃** ⇒ 自动回复从未进登记表。
专项采集用 `scripts/扫描自动回复.py`（产出 `.workbuddy-ai/自动回复全量.json`）。

### 4. 🔴 「跟进次数」不能只看发件箱 —— 要核对**发到了哪个地址**
跟进队列是按**跟进表的「邮箱」字段**构建的。若回复/自动回复里的**联系人变更未写回跟进表**，
队列会**一直发到已失效地址**，统计上"跟进次数=1"，**实际等于没跟进**。

**2026-10-05 实测两例**：
- **Valard**：09-24 收自动回复「{{CONTACT_NAME}} 已离职，转 `ssousa@`」→ 09-25 已改投 →
  **09-29 跟进信又发回 `ksones@`** ⇒ `ssousa@` 实际 **0 次跟进**。
- **{{COMPANY}}**：09-29 已知联系人变更为 `matthew.zold@` → **10-02 跟进信仍发 `utilitysalescanada@`**。

**核查方法**：按域名拉全部发送记录，逐条看 `to`，把「发给谁」和「该发给谁」对齐。
**建议闸门**：跟进表增列「地址有效性」（有效/已离职/已退信/待核），构建队列时拦下失效收件人。

## 邮件认证（SPF / DKIM / DMARC）检查 —— 退信率的根因排查

**怀疑「服务商拒收」类软退信时，第一件事查这个。** DNS 查询不受本机 TUN 劫持影响（实测可用）：

```bash
dig +short TXT <domain> @8.8.8.8                    # SPF
dig +short TXT _dmarc.<domain> @8.8.8.8             # DMARC
for s in dkim default tencent mail qq; do \
  dig +short TXT $s._domainkey.<domain> @8.8.8.8; done   # DKIM（试多个选择器）
```

**`jiezougroup.com` 实测（2026-10-03）**：MX ✅ ｜ SPF ✅ `~all` ｜ **DKIM ❌ ｜ DMARC ❌**

### 🔑 DKIM 与 DMARC 的获取方式根本不同
- **DKIM = 后台「生成」**（腾讯企业微信：协作→邮件→安全管理→DKIM验证→配置），私钥在邮局，**不能自己造**
- **DMARC = 自己「写」**，**无生成入口**，DNSPod 加 TXT `_dmarc`

### ⚠️ 与腾讯官方文档的分歧（我们的做法更保守）
官方示例是 `p=reject`，**但必须先用 `p=none`** —— 若 DKIM 未配好、且有第三方在用该域发信，
`reject` 会立刻拒收正常业务邮件。顺序：`none` →（2–4 周）→ `quarantine` →（2 周）→ `reject`。

详见项目文件 `操作指南-DKIM与DMARC配置-腾讯企业微信.md`。

## 效果诊断：必须用「成熟窗口」算回复率

**整体回复率会被刚发出的批次稀释**（新发客户还没到回复窗口）。
必须先按「首封距今天数」分组，再算：

```python
mature = [k for k,t in first.items() if (NOW - t).days >= 8]   # 首封 ≥8 天
reply_rate = len(mature & reply_keys) / len(mature)
```

本项目 2026-10-03 实测：整体 8/238 = 3.4%，**成熟窗口 8/120 = 6.7%** —— 差一倍。
**报告时必须两个都给，并注明口径。**

## 行业基准（B2B cold email 2026，用于判定「什么水平」）

| 指标 | 优秀 | 良好 | 中位 | 红线 |
|---|---|---|---|---|
| 回复率 | 8–12%（top 10%） | 7%+ | 3–6% | <2% = 名单或送达出了问题 |
| 明确意向率（opportunity rate） | 2%+ | 1–2% | 0.5–1% | <0.5% |
| 退信率 | <2% | 2–3% | — | **>3% 立即暂停**（Google/Microsoft 硬性限制） |
| 回复中含意向占比 | — | — | 20–30% | — |

跨行业平均回复率 **3.4%**（7000 万+ 封样本）。**制造业 top 区间 7–10%**。
出处：Built for B2B《B2B Cold Email Benchmarks 2026》、Belkins 2026、Empra 2026。

### 本项目基线（2026-10-03）
成熟窗口回复率 **6.7%**（中位偏上，逼近优秀线）｜意向率 **1.68%**（良好）｜
回复含意向占比 **50%**（远优于行业 20–30%）｜**退信率 7.6%（超标 2.5 倍，最大风险）**

### 🔴 必须剔除「手工批次」—— 否则退信率会虚高 4 倍

**用户 2026-10-03 明确**：`9/15`、`9/17`、`9/18`、`9/23`、`9/25`、`9/30` 这 6 天的发送
**未走项目邮箱验证、是手工发出的**，不计入项目基线。

```python
EXCL = {'09-15','09-17','09-18','09-23','09-25','09-30'}
cust = [k for k,t in first.items() if t.strftime('%m-%d') not in EXCL]   # 项目批次
```

本项目实测对比（**结论完全相反**）：

| | 手工批次（未验证） | 项目批次（走验证） |
|---|---|---|
| 触达客户 | 60 家 | **178 家** |
| 退信 | 12 家（**20.0%**） | **3 家（1.7%）** |
| **硬退信（地址不存在）** | **5 家** | **0 家** |

**⇒ 项目批次硬退信为 0，证明验证环节有效。**
**报退信率时若不剔手工批次，会把 7.6% 的锅算到项目头上**（v1 报告犯过这个错）。

### 退信率必须分档算（本项目已验证的关键结论）
- **角色邮箱（`info@`/`sales@`/`contact@`…）：11.9%**
- **具名邮箱：4.4%**
- 差 **2.7 倍** —— 这是「B 档停发」决策的量化依据。

### 退信时间分布：看「当日退信率」，不要看「退信条数」

**退信条数多的那天，往往只是发得多** —— 两个口径会得出相反结论。

```python
# 必须把「退信数」除以「当日对外发送量」
per_day_sent = Counter(...)   # 当日含外部收件人的邮件数
bounce_day   = Counter(...)   # 当日首退条数
rate = bounce_day[d] / per_day_sent[d]
```

本项目 2026-10-03 实例：
- 9/23 退 6 条（看着最多）→ 当日发 28 封 → **21.4%，真异常**
- 9/24 退 1 条 → 当日发 44 封 → 2.3%，正常
- 9/29 退 1 条 → 当日发 75 封 → 1.3%，正常

**同时必算「退信率按时期」**（本项目：9/15–9/20 = 25% → 9/21–9/27 = 6.3% → 9/28–10/3 = 3.3%），
这能看出**名单质量是在改善还是恶化**。

⚠️ **近期批次的退信率会低估** —— 异步退信（Barracuda / M365 延迟）还没回完。
本项目实测 15/20 条延迟为 **+0 天**（同步退信为主），但近 5 天的批次仍需留观察期。

## 环节归因：回复率高 + 退信率高 = 瓶颈在①不在②

| 症状 | 归因 | 动作 |
|---|---|---|
| 回复率 <2% | 名单或送达坏了（**通常不是文案**） | 查送达与名单质量 |
| 回复率 3–6% | 中位 | 提升个性化与 CTA |
| 回复率 ≥7% | top-quartile | **别再改文案，去扩量** |
| 退信 >3% | 名单质量 | 发送前强制验证 |
| 回复率与退信率背离（都高） | **信对了、路没铺好** | 资源投「验邮箱」而非「改文案」 |
