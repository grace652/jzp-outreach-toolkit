# 开发信发送链路：定时、合规闸门与项目接入

> 2026-09-27 实测沉淀。补齐 `邮件通道接入.md` 没覆盖的三块：
> ① 定时发送到底能不能做 ② 发信前的合规闸门 ③ 接入外部项目时的纪律。

---

## 一、定时发送：协议层做不到，只能本机队列

### 四条通道逐一实测，全部排除服务端定时

| 通道 | 实测结果 |
|---|---|
| **SMTP** | ❌ 协议本身**没有定时能力**，只有"立即投递"。用户手动发信时的「定时发送」是**客户端/服务端功能**，不是协议能力 |
| **IMAP** | ❌ 无调度扩展。实测腾讯企业邮 CAPABILITY = `IMAP4, IMAP4REV1, XLIST, MOVE, IDLE, XAPPLEPUSHSERVICE, AUTH=LOGIN, AUTH=PLAIN, NAMESPACE, CHILDREN, ID, UIDPLUS` —— 无任何 scheduling 扩展 |
| **Exchange EWS** | ❌ 端点不可用。`ex.exmail.qq.com:443` 端口通，但 `/EWS/Exchange.asmx` 返回 **502**、`/ews/exchange.asmx` 返回 **403（Wwebsvr）** |
| **网页版定时发送** | ⚠️ 功能**存在**（exmail.qq.com → 写邮件 → 定时发送），但是 UI 功能；**扫码登录**的账号难以复用会话做自动化 |

### 结论与替代

**做不到服务端定时**，但**本机定时队列可实现效果等价**：

```
邮件先排好队 → 到点由脚本投递
```

**唯一代价**：运行时段**电脑需开机联网**（服务端定时则关机也照发）。

> ⚠️ 向用户说明时务必讲清这条取舍，不要含糊成"可以定时"。

### 时区窗口算法（冷邮件分散发送）

**目标时刻 = 对方当地上午 9:00–10:00**（刚上班，邮件在最上面）

```
北京发信时间 = 9:00 − 对方时区偏移 + 8
```

| 时区 | 夏令时北京窗口 |
|---|---|
| 美东 ET | 21:00–23:00 |
| 美中 CT | 22:00–24:00 |
| 美山 MT | 23:00–01:00（次日） |
| 美西 PT | 24:00–02:00（次日） |
| 阿拉斯加 AK | 24:00–02:00（次日） |

**必须自动处理的三件事**：
1. **夏令时**（北美：3月第2个周日 → 11月第1个周日；冬令时 +1 小时）
2. **跳过周末**（周六周日不发）
3. **跨日**（窗口起点 ≥24 点要 +1 天）

**实现要点**：
- 窗口用 `(起, 止)` 元组存，>24 表示次日，避免跨日判断散落各处
- 队列每发一封就落盘一次 → 中断也不丢状态
- `--run` 设计成**可反复调用**（每 30 分钟跑一次），只发窗口已到的
- 踩过的坑：`datetime` 的 **aware / naive 混用**会报
  `TypeError: can't compare offset-naive and offset-aware datetimes` ——
  比较前两边都 `.replace(tzinfo=None)`

## 二、发信前的合规闸门（自动化红线自检）

发信脚本必须在发送前跑一遍自检，**不通过就拒绝发送**。清单：

```
[ ] 无禁用认证表述（CSA Certified / SASO / SONCAP）
[ ] 无禁用品牌（同行名，如 YAWEI）
[ ] 首封无交期数字（正则 \d+\s*weeks?）
[ ] 首封无价格词（price / quote / FOB / USD / discount / MOQ）
[ ] 无 spam 触发词（free / discount / best price / limited time /
    click here / guarantee / 100% / !!!）
[ ] 含退订承诺句（CASL / CAN-SPAM 强制）
[ ] 结尾格式符合规范（正文不带职务/邮箱/电话行）
[ ] 词数在区间内（首封 60–150 词）
[ ] 无占位符残留（【待填】之类）
```

**两个容易做错的地方**：

1. **署名主体检查要查「签名」而不是「正文」** ——
   新格式下正文止于姓名，公司名由签名承担。查错地方会误报。
2. **`unsubscribe` 这个词不在 spam 词表里** ——
   禁的是**群发式的** `Click here to unsubscribe`（模板标志），
   不是退订这个行为本身。把退订词当 spam 禁掉 = **合规事故**。

## 三、接入外部项目时的纪律（血的教训）

### 🔴 只做拷贝，绝不修改原文件

用户把整个项目交给你接入时，**那仍然是他的资产**。

```
✅ 正确：cp -R 源目录 目标目录   → 在新位置处理
❌ 错误：顺手"升级"源目录里的旧文件
```

**"升级旧内容"必须先问。** 即使用户抱怨"这些旧文件不合新规范"，
也不要批量改——那些可能是他正在用的生产资产。

### 接入后必须做的一致性验证

```bash
# 逐项 diff，证明没动原文件
for f in <文件名列表>; do
  diff -q "$SRC/$f" "$DST/$f" >/dev/null && echo "一致" || echo "有差异：$f"
done
```

**结果要主动报给用户**（「7/7 指令文件一致，125/125 信件一致」），
这比一句"我没改"可信得多。

### 另一个坑：工作区文件可能被外部改写

实测遇到：自己写的定义文件在 **几分钟后被改写**（内容被大幅重写，
关键定义被改反）。来源可能是用户、他的另一个 agent、或某个 hook。

**应对**：
1. 写完关键定义文件后，**下次读取时先校验内容是否与预期一致**，不要假设还是自己写的样子
2. 发现不一致 → **停下来问用户**，不要自己猜哪个对（用 AskUserQuestion 给出两个具体选项）
3. 用户确认后，**全文扫描**把残留的旧定义都改掉（一次改一处容易漏）

## 四、完整的发送链路（可直接复用的分层）

```
① 写作层   写开发信 agent 产出 .md
           （正文 ①–⑤ 由它负责，发送层不管内容质量）
             ↓
② 组装层   抽正文 → 接图片签名 → 红线自检 → 生成 HTML
             ↓
③ 排程层   按收件人时区算北京窗口 → 入队
             ↓
④ 投递层   SMTP 投递（到点由定时器触发）
```

**分层的好处**：写作质量与投递可靠性解耦。写作 agent 换人/换模型，
投递层不用动；投递方式从 SMTP 换成 API，写作层也不用动。
