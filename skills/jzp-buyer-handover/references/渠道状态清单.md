## 五之二、🔴 SMTP RCPT 探测：M365 会拉黑来源 IP（2026-09-28 实测踩坑）

> **适用工具**：`jzp-americas-dev/邮箱验证.py`（本轮新增）。
> **能做的事**：在**非 catch-all** 域名上，用 RCPT 250/550 判定具名邮箱是否真实存在。
> 🔴 **但它有一个致命的假阴性陷阱，必须按下面的方法用。**

### 现象（本轮真实经过）

对 `{{COMPANY_DOMAIN}}`（M365 / Exchange Online）探测：

| 轮次 | `info@`（官网明文，**已知真实**）| `mario.dibella@`（候选人）| 判读 |
|---|---|---|---|
| 第 1 轮 | **250** | **250** ✅ | 可信 —— 候选命中 |
| 第 2 轮（数分钟后）| **550** ❌ | **550** | 自相矛盾 |
| 第 3 轮 | 半程 550 / 半程 250 | — | 拉黑在抖动 |

**第 2 轮的拒绝原文：**
```
550 5.7.1 Service unavailable, Client host [223.64.2.43] blocked using Spamhaus
```

### 根因

M365 对 SMTP 收件人探测有**主动反制**：探测若干次后，把来源 IP 丢进 Spamhaus 黑名单，
**随后连 `info@` 这种确定存在的地址也返回 550**。
→ 若不设控制地址，会把**真实存在的邮箱判成不存在**（事故 B 的加强版）。

### 🔴 强制规程：控制地址（Control Address）

**每轮探测的第一次 RCPT 必须是「该域已知真实」的地址**（通常 `info@`，取自官网明文）：

| 控制地址结果 | 含义 | 动作 |
|---|---|---|
| **250** | 本轮探测有效 | 继续走 catch-all 判定 + 对照组 + 候选 |
| **550 / 其它** | 🔴 **本轮整体作废** | ⛔ **绝不能据此判候选『不存在』**；换渠道，或隔一段时间再试 |

**配套判定（缺一不可）：**
1. 控制地址必须 250（否则作废）
2. 随机地址必须 550（排除 catch-all）
3. 对照组（`john.smith@` 等 3 个格式正确但不存在的姓名）必须全部 550（排除网关宽松）
4. 候选 250 才可采信

### 操作纪律

- 🔴 **不要连续多轮重复探测同一域** —— 会加速拉黑，且结果自相矛盾。**一轮为准。**
- 🔴 **拿不到可靠结果就换渠道**（官网/LinkedIn/州采购门户/电话），**不要反复重试**。
- ⚠️ 被拉黑是**来源 IP** 层面的，不是域名层面的 —— 换个域探测仍可能被同一 IP 拖累。
- ✅ 对**非 M365** 的域（如自建 Postfix、Google Workspace）通常没有这个反制，但**仍要走控制地址**。

> 📌 **这条也是对 skill 主文件「验证闸门时要用闸门自己的函数」的补充**：
> 不仅要"用真函数"，还要**给闸门喂一个已知为真的样本**，否则闸门坏了你也看不出来。

### 🔴 命名规则探测法：不要只试一种格式（2026-09-28 买家 135 实证）

**常见误区**：拿到「名 姓」就只试 `{first}.{last}@`，失败即判「邮箱拿不到」。
**实证**：{{COMPANY}}（`{{COMPANY_DOMAIN}}`）的真实规则是 **`{firstname}@`**：

| 探测地址 | 结果 | 判读 |
|---|---|---|
| `{{CONTACT_EMAIL}}` | 550 | 假设【名.姓】：**失败** |
| `{{CONTACT_EMAIL}}` | 550 | 假设【首字母+姓】：**失败** |
| **`{{CONTACT_EMAIL}}`** | **250** | ✅ **命中**（本域规则 = `{firstname}@`）|

**⇒ 规程：候选地址必须按多套命名规则并行探测，至少覆盖以下 4 套：**

```
① {first}.{last}@       例 john.smith@
② {first}@              例 john@          ← 小公司/短域名常见，最易被漏
③ {f}{last}@            例 jsmith@
④ {last}@               例 smith@
（可选）{first}{last}@ / {f}.{last}@ / {last}.{first}@
```

**纪律**：
- 🔴 **不要把「{first}.{last}@ 被拒」当成「本域无实名邮箱」** —— 换格式再试。
- 🔴 **但命中后必须用控制地址法复核**（见上节）：同一轮里 `info@` 必须 250、随机地址必须 550。
- ⚠️ 不同域的规则常常不同，**同一批客户不要假设规则一致**。

### 🔴 网关「对未授权来源不透露目录」（2026-09-28 买家 132/133 实证）

两种**让 SMTP 探测整体失效**的网关行为，机理不同，结论一样（**都不能用于判定**）：

| 类型 | 症状 | 实例 |
|---|---|---|
| **catch-all** | **任何**地址（含随机）一律 **250** | 买家 131 `{{COMPANY_DOMAIN}}` |
| **统一拒绝未授权来源** | **任何**地址一律 **550 5.4.1 Access denied**，连控制组 `info@` 也 550 | 买家 132 `{{COMPANY_DOMAIN}}`（Mott 集团租户）|
| **区域路由拦截** | 一律 **451 4.4.62 wrong Office 365 region** | 买家 133 `hoopercorp.com`（mtaroutes 网关）|
| **不透露目录 + 授权门槛** | 控制组（已知真实地址）返回 **451 not authorized**，随机地址返回 **550 no mailbox** | 买家 133 `hoopercorp.com` |

**⇒ 判读纪律**：
- 一律 250 → catch-all，**不能说地址存在**
- 一律 550 且**控制组也 550** → **本轮作废**，不能说地址不存在
- 控制组 451 / 451 类 → **无法建立「真地址→250」基准** → **本轮作废**
- 🔴 **唯一可信的情形**：控制组 250 + 随机地址 550 + 候选 250（三者同时成立）

## 六、🔴 catch-all 域清单（SMTP 探测永久无效）

**判据**：向**随机编造地址**发 RCPT，若返回 250 ⇒ 该域为 catch-all ⇒ **SMTP 探测对本域毫无意义**（任何地址都 250）。

| 域 | 公司 | 批次 | 影响 |
|---|---|---|---|
| `{{COMPANY_DOMAIN}}` | {{COMPANY}}（BC）| 131 | 只能用 B 档 `info@`，具名邮箱无法验证 |
| `{{COMPANY_DOMAIN}}` | {{COMPANY}}（ON）| 137 | 具名邮箱靠官网第一方来源定 A 档，**不依赖 SMTP** |

**⚠️ catch-all 的三条连带后果（发送环节必知）：**
1. **无预验证手段** —— 只能靠**退信（bounce）**判断可达性。
2. **推断格式风险更高** —— 常规域里"SMTP 不 250 就说明格式错"，catch-all 域里**永远 250**，
   臆造地址（如 `sweatherby@`）不会被证伪，**直接触发 H2 违规**。⇒ catch-all 域**严格禁止使用非第一方来源地址**。
3. **不可与"命中"混淆** —— 若不做随机地址对照，会把 catch-all 误判为"全部命中"。

> **规程**：探测任何新域，**第一发必须是随机地址**（如 `zzz_nonexistent_probe_9987@`）。
> 250 ⇒ 标记 catch-all，本轮全部结果作废，改走第一方来源。

## 九、🔴 邮箱所在域已失效 —— 必须查 A/MX/whois 后才可交付

**案例（买家 144 {{COMPANY}}）**：
官网 Contact 页明文列出具名邮箱 `{{CONTACT_EMAIL}}` / `{{CONTACT_EMAIL}}`，
**看似 A 档**。但实测：

```
dig @8.8.8.8  +short A {{COMPANY_DOMAIN}}     → （空）
dig @1.1.1.1  +short A {{COMPANY_DOMAIN}}     → （空）
dig @9.9.9.9  +short A {{COMPANY_DOMAIN}}     → （空）
dig +short NS {{COMPANY_DOMAIN}}              → （空）
whois {{COMPANY_DOMAIN}}                       → Not found: {{COMPANY_DOMAIN}}
```

⇒ **该域未注册 / 已过期** ⇒ **官网列出的具名邮箱全部不可投递**。
实际可用路径是页脚的 `{{CONTACT_EMAIL}}`（微软免费邮箱）。

**规程（三步，缺一不可）**：
1. **A 记录**：`dig @8.8.8.8 +short A <域>`
2. **MX 记录**：`dig +short MX <域>` —— **无 MX ⇒ 该域不收信**
3. **whois**：`whois <域>` —— 查 `Not found` / 到期日

⚠️ **本机有 fake-ip DNS 劫持** ⇒ **必须用 `@8.8.8.8` / `@1.1.1.1` / `@9.9.9.9` 三处交叉**，
三处一致才可信（Bradmoore 案例即三处一致为空）。

## 二十一、🔴 第 7 类 SMTP 探测失效网关：Proofpoint ARS「转发式 250」（2026-09-28 买家 147 实证）

**现象**：向 Proofpoint ARS 网关发 RCPT，**任何地址**（含随机编造）都返回：

```
250  zzz_nonexistent_probe_9987@example.com :: …will relay to a client address
250  info@example.com                        :: …will relay to a client address
```

**判据**：**回执文本含 `will relay`** ⇒ 该网关**完全不验证收件人**，只做转发 ⇒ **探测无效**。

| 特征 | 说明 |
|---|---|
| MX 主机名 | 形如 `<domain>.1.0001.arsmtp.com` / `<domain>.2.0001.arsmtp.com` |
| RCPT 响应 | **恒 250** + `"will relay to a client address"` |
| 与 catch-all 区别 | catch-all 是**收件方**策略；ARS「转发式 250」是**网关**行为，**更隐蔽**（有明确文字标识）|

**⚠️ 主机名解析坑（同案实测）**：
应用 `smtplib` 连 ARS 时，**必须使用 MX 记录里的原始主机名**（含点号、**不可把下划线改连字符**）：
- ✅ 正确：`earlcarrelectriccanada.com.1.0001.arsmtp.com`（dig 可解析）
- ❌ 错误：`earlcarrelectriccanada-com.1.0001.arsmtp.com`（自行替换字符 → `gaierror`）

**⇒ 规程**：
1. 见到 `will relay` ⇒ **立即判定该域 SMTP 不可用**，改走其他渠道。
2. **同一公司的邮箱可能在另一个域上**（买家 147：网站域被 ARS 挡，**邮箱域 `ececl.ca` 却是 M365 且探测有效**）

**判据（决定性）**：**随机对照地址亦返回同一 550** ⇒ 属**源 IP 级拦截**，与收件人存在性**完全无关**。
⚠️ **不可据此判断「地址不存在」** —— 仅说明**该域不接受来自本探测源的 RCPT 查询**。

**本批次命中**：

| 买家 | 公司 | MX |
|---|---|---|
| 172 | {{COMPANY}}（Sonepar 旗下） | `de-smtp-inbound-1.mimecast.com` |
| 173 | {{COMPANY}}（USESI 成员） | `us-smtp-inbound-1.mimecast.com` |

### 🔴 与既有「源侧」失效类别的区分（重要）

三类都是**源侧问题**（与我方发信域无关），但**拦截阶段不同**：

| 类别 | 例 | 拦截阶段 | 报错 |
|---|---|---|---|
| **(j)** ISP 源 IP 封禁 | Steinmetz（Charter/Spectrum） | **CONNECT 阶段** | `554 ... 223.64.2.43 blocked` |
| **(k)** rDNS 策略拒 | AESCO（IONOS/1&1） | **CONNECT 阶段** | `554 ... Invalid DNS PTR resource record` |
| **(l)** **Mimecast + Spamhaus PBL** | **NEDCO / EWNE** | **RCPT 阶段** | `550 zen.mimecast.org Listed by PBL` |

> **操作含义**：
> - (j)/(k) → **TCP 都连不上**，任何探测都无效
> - (l) → **连接与 `MAIL FROM` 均通过**，仅 `RCPT` 被拒 ⇒ **最易被误读为「地址不存在」**
> ⇒ **遇 Mimecast MX 可直接预判：不可探测，不要浪费轮次试格式。**
> ⇒ 这**不构成对目标公司的负面判断**，仅说明**探测手段受限**；转写信环节仍可投递（用正规 ESP）。

|---|---|

**但它对下游是真实风险**：写信环节 `grep "买家99"` 会一次命中三家不同公司。

### 32.1 ✅ 交付前的编号体检（每条批次收尾时执行）

```bash
cd <批次目录>
ls 买家*.md | sed 's/买家\([0-9]*\)_.*/\1/' | sort -n | uniq -c | awk '$1>1'
# 无输出 = 编号唯一；有输出 = 存在冲突，逐个处理
```

### 32.2 冲突处置三方案（用户 2026-09-28 选定 A）

| 方案 | 做法 | 代价 | 适用 |
|---|---|---|---|
| **A（推荐）** | 建批次汇总 `_批次汇总.md`，显式登记 §冲突清单 + §全量索引（编号↔公司↔**文件名**），并声明**按文件名取用** | 低 | 内容无损，只要可用 |
| B | 批量重编号 + 改文件名 + 扫全库交叉引用 | **高** | 强制编号唯一 |
| C | 目录放 `⚠️编号冲突说明.md` 提示 | 极低 | 只要提醒 |

> ⚠️ **为什么默认不选 B**：旧编号已被其他文件/文档交叉引用，重编号的**引用清扫风险大于收益**。
> 只要索引表把「文件名」确立为唯一取用键，编号冲突就不再造成误取。

### 32.3 🔴 铁律：文件名 = 唯一取用键

- ✅ 取用交接单**一律按文件名**（文件名全局唯一）
- ❌ **禁止**用编号做批量定位 / 排程主键 —— 冲突号会撞库
- ⚠️ 引用编号时必须**带上公司名**，写作「买家 99（Intel Electric）」

### 32.4 编号起算规则（避免复发）

新批次编号**从上一批最大值 +1 起算**（batch5 用至 173 ⇒ 下一批从 **174** 起），
**不再沿用批内滚动序号**。批次收尾时跑一次 §32.1 脚本，冲突立即暴露。

# 🔴🔴 2026-10-02 batch9：排重基线漏掉「成交客户 SGE」——**长度过滤把 3 字母名静默丢弃**

## 一、事故

当新线索报上来，而且通过了排重。** 而它**是我方 2023-07 的已成交客户**

**这与 batch7 的 Black & McDonald 事故同型 —— 又一次「把已成交客户当新客户」。**

## 二、根因：`norm()` 后的长度过滤

```python
k = norm(kw)
if len(k) < 4:        # ← 罪魁
    continue
```
`norm("SGE")` = `"sge"`，长度 3 ⇒ **被静默丢弃** ⇒ 基线里根本没有 `sge`
⇒ **所有 ≤3 字母的公司名都不受基线保护**。

**受影响的类型**：全大写缩写型公司名（SGE、CVE、TM3、IES…），
以及任何短名 —— 而**成交客户里恰好有 SGE 这种 3 字母名**。

## 三、修法（两处，缺一不可）

### ① `build_baseline.py`：阈值 4 → 3
```python
if len(k) < 3:        # 3 字母也要保留
    continue
```
基线规模：**923 → 941 词**（`sge` 已入册）。

### ② `check_dedup.py`：**长度 < 5 的关键词只做「全词匹配」**
```python
# 子串：仅限「关键词 >= 5 字符」且两侧都 >= 8 字符
if len(k) < 5:
    continue
idx = n.find(k)
if idx > 0 and len(n) - (idx + len(k)) >= 8:
    hits.append((k, src, "子串(两侧>=8)"))
```

> 🔴 **两处必须配套**：只降阈值不收紧匹配方式，`k line` 这类短词会疯狂误报
> （`allteck line`、`franklin empire`…）；只收紧不降阈值，短名继续漏。
