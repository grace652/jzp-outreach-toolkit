# 步骤2 邮箱 waterfall 优化方案（正式结论文档）

> 📁 **归档位置**：`project2/buyers/_series/`（方法论专项，非买家交接单）
> 背景：用户痛点 —— **「有时候整个项目只给我官网的 info@ 类邮箱，这种邮箱价值很低」**。
> 目标：**尽可能找到关键人的邮箱和其他联系方式**。
> **适用地区：美国 + 加拿大**（用户明确主攻这两地区；非北美角色习惯不在本方案范围内）。
> 调研日期：2026-09-23｜来源：Clay / Hunter / Netrows / connectsafely.ai / gracker.ai / LeadCRM / Seamless.ai / Happierleads
> **状态：✅ 已实施（2026-09-23）** —— 落地方见文末第七节。

---

## 一、现有 waterfall 的问题诊断

现行（`01-methods.md` §5.9）：
```
L0官网 → L1政府 → L2DNS+命名规则 → L3 B2B库 → L4社媒 → L5黄页 → L6电话 → L7付费API
```

**三个结构性问题**：

| # | 问题 | 后果 |
|---|---|---|
| **P1** | **先找邮箱、后找人** —— L0 就在抓 `info@`，人是最后才确认 | 拿到一堆无人格的通用邮箱就开始"完成"了，**这正是用户说的"价值很低"** |
| **P2** | **`info@` 被当成"兜底结果"**，而不是"必须突破的中间态" | 找到 `info@` 就停了，没有"从 info@ 升级到具名决策人"的强制动作 |
| **P3** | **推演缺乏可执行阶梯** —— 只说"只能备选"，没说"备选怎么逐个试真" | 推演邮箱要么不敢用、要么盲发退信 |

> **业内共识**（Clay 指南原话）：**"a domain to verified email is a narrowing chain"** ——
> `域名 → 公司 → 正确的人 → 已验证邮箱`，**每一步都应收窄范围**。
> 而"只给 info@"的失败模式，正是 **链条在第 3 环就断了**（没锁到"人"）。

## 二、可借鉴的成熟方案（4 条核心原则）

### 原则 1：先锁「人」，再找「邮箱」（顺序反转）
Clay 六步法的前 4 步**全是找人**，第 5 步才找邮箱：
1. 域名 → 公司实体（注意**母子关系**：采购权可能在母公司）
2. **定义"谁是决策人"** —— 不是"VP 以上"，而是**相对你这单的角色**
3. 按**职能+层级**筛人（不是精确头衔，因为同角色有三种叫法）
4. **用公开信息确认这个人还在职**（"still_here" 标记 —— 避免发给三个月前离职的人）

> **对我们的启示**：waterfall 应改为 **先出「人」清单，再对每个人跑邮箱链**。
> 一个 `info@` 价值低，是因为**它背后没有人**；**先找到一个具名的、在职的、职能对口的人**，才是一切的前提。

### 原则 2：`info@` 是「角色邮箱」，必须显式分级处理
Clay 的验证闸门把邮箱分为：`Valid / Invalid / Catch-all / Unknown / **Role-based**`，
并明确指令：**"suppress Role-based and free-webmail addresses before they enter a personalized sequence"**。

> 原话：**"A role inbox like `info@` or `sales@` reaches a room no one owns."**
> （角色邮箱 = 送达一间没人的房间）

> **对我们的启示**：
> - `info@` / `sales@` **不应作为"主送结果"交付**，而应标记 **`Role-based`**
> - 它只有两个合法用途：① **点名转交**的入口 ② 免费 webmail（如 Gmail）另类对待
> - 交付时**明确区分**「决策人直邮」/「角色邮箱」/「免费邮箱」三档

### 原则 3：邮箱填隙用「多源瀑布」，不选单一工具
Clay 实测数据（**质量 / 覆盖率**）：

| 工具 | 质量 | 覆盖率 |
|---|---|---|
| Hunter | **97.15%** | **52.87%** |
| Findymail | 96.26% | **90.26%** |
| Wiza | 94.72% | 85% |

> **关键结论**：**单一工具最多只覆盖一半名单**。正确做法是**串行瀑布**（跑第一家→命中即停→没命中再跑第二家）。
> 另：**免费第一步可先"推断"邮箱**（name+domain 按 `first.last@` 构造）—— Clay 实测 **约 31% 无需调用任何 provider 就能构造出有效地址**。

> **对我们的启示**：L2 的"命名规则推演"不该被当成低价值备选，而应**前置为免费第一跳**（命中率约 1/3）。

### 原则 4：验证是「闸门」，且要按风险选策略
- **没有默认验证 = 不合格**。必须显式加验证，并开"**Require validation success**"
- 结果分级：`Valid / Invalid / Catch-all / Unknown / Role-based`
- **Catch-all 看着有效但可能退信**——要单独标注
- 输出**变小是正确结果**（"that is the correct outcome"）

> **对我们的启示**：现有"≥4 分才可主送"是对的，但缺一条：**`catch-all` 域名要独立扣分并标注**（现已 -2，可强化为"必须电话确认"）。

## 三、优化方案（建议改法）

### 3.1 结构调整：把「找人」提到最前（新增 L-1 层）

```
【新增】L-1 先锁定「具名决策人」
  - 定义买家类型 → 决定要哪类角色（终端找工程/采购；分销商找采购/品类经理）
  - 用公开源拿到「姓名 + 职能 + 在职证据」三件套
  - ⚠️ 无具名决策人 → 不允许进入邮箱环节（除非用户接受角色邮箱）
      ↓ 拿到人之后，才对这个人跑 L0–L7
L0 官网全量 → ... → L7 付费API（不变）
```

**这是本次最核心的改动**：`info@` 不再是"结果"，而是"**触发继续找人**的信号"。

### 3.2 新增「角色邮箱升级动作」强制项

当**唯一收获是 `info@` / `sales@`** 时，**不得直接交付**，必须执行升级三步：

| 步 | 动作 | 依据 |
|---|---|---|
| **① 挖角色邮箱** | 逐个读 Contact / Team / Careers 页，找 `Supplier@` / `Owners@` / `Estimating@` 等**职能邮箱**（比个人推演邮箱还好用） | 现行 §5.5b 优先级 0 档 |
| **② 从 info@ 反推命名规则** | 若曾收到该域名的任何真实回信，其**显示名/签名**常暴露真实格式 | 一线经验 |
| **③ 免费先试推演** | 按 `first.last@` 等构造，**约 1/3 命中**，成本≈0 | Clay 实测 31% |

> 🔴 **交付纪律**：若三步都失败，交接单必须写
> **「仅取得角色邮箱 `info@`，未取得决策人直邮」**，并**标注为风险**，而不是混在"邮箱"字段里蒙混过关。

### 3.3 邮箱结果分三档标注（新增交付标准）

| 档 | 类型 | 是否可主送 | 交付写法 |
|---|---|---|---|
| **A** | 具名决策人邮箱（Valid） | ✅ 主送 | `姓名 <邮箱>` + 验证状态 |
| **B** | 角色邮箱（Role-based） | ⚠️ 仅**点名转交** | `info@`（角色邮箱，建议点名转交） |
| **C** | 免费邮箱 / Catch-all | 🔴 需电话确认 | 标注 + 电话验证建议 |

### 3.4 把「推演」从备选升级为「可执行阶梯」

现行只说"备选、标未验证"。建议补一条**逐个实测顺序**（不批量盲发）：
```
{first}@ → {first}.{last}@ → {last}@ → {fi}{last}@ → {fi}{li}@
```
配合 §5.8 对照测试（先测已知真实的 `info@` 排除假阴性）。

| 优先级 | 改动 | 收益 | 成本 |
|---|---|---|---|

## 五、结论

**用户直觉是对的**：`info@` 价值低，**因为它背后没有人**。

**根本解法不是"更努力地找邮箱"，而是"把找人的顺序提前"** ——
先锁定一个**具名的、在职的、职能对口的决策人**，再为这个人找邮箱；
`info@` 从此只承担两个角色：**点名转交的入口** + **命名规则的样本源**。

## 六、追加调研：LinkedIn 如何发挥最大作用（2026-09-23 联网核实）

> 用户补充要求：「还有一个我需要把 LinkedIn 在其中的作用发挥出来」。
> 以下为对 5 个业内来源的核实结论。

### 6.1 关键结论：LinkedIn 的价值不在"找邮箱"，在"**定义人**"

**业内共识**：LinkedIn 是**唯一同时具备「具名 + 在职 + 职能 + 层级」四个维度的免费公开源**。
邮箱工具（Hunter/Apollo）只能回答"这个域名下有没有这个人"，**不能回答"这个人还在不在、还管不管这块"**。

→ 因此 **LinkedIn 必须双岗定位**：

```
【L-1 第一岗：找人】  ← LinkedIn 在这里是主引擎
   锁定「具名 + 在职 + 职能对口」的决策人
        ↓ 拿到人之后，才对这个人的名字跑邮箱链
【L4 第二岗：核验】  ← LinkedIn 在这里是印证人
   头衔核验 + still_here 在职核验 + 补兜底
```

### 6.2 可直接吸收的 5 条外部结论

| 来源 | 结论 | 落到哪里 |
|---|---|---|
| **connectsafely.ai（2026）** | **决策人头衔随公司规模漂移**：1–10人→Owner/CEO/Founder；10–50→VP/Director；50–500→部门负责人；500+→区域总监/采购团队。另给 3 条 LinkedIn-only 找人路径：①公司页 **People 区**按 Function/Seniority 筛 ②借连接**反推组织图**（谁 tag 谁 / endorsement / "People also viewed"）③先连员工再请引荐 | **L-1 岗位映射表**（买家类型 × 规模 → 角色词） |
| **gracker.ai（2026）** | LinkedIn **只有 3 个字段吃 Boolean**（Global 关键词 / **Current Job Title** / Company）；运算符**必须大写**；**只能用直引号**（弯引号**静默失败**）；免费版 **OR 上限 3–4 个**；不支持通配符/临近搜索；语法错时**不报错，静默跑一个"改良后"的搜索** | L-1 的 query 纪律 + 免费档限制说明 |
| **LeadCRM（2026）** | 从 LinkedIn 个人页取邮箱的**免费四步**：① **Contact info** 标签（命中率约 **30%**）② **About 区 Ctrl+F** 搜 `gmail` / `at` / `dot`（用户常做反爬混淆）③ **Google X-Ray**：`site:linkedin.com/in/ "<人名>" "@<公司域名>"` ④ 推演+验证 | L-1 完成后的取信动作 |
| **Seamless.ai（2026-08）** | 🔥 **衰减硬数字**：约 **2.1%/月**；**65.8%** 的人 12 个月内换岗/换职能；**37.3%** 的邮箱 12 个月内失效 | **still_here 在职核验** |
| **Happierleads（2026-09）** | 🔥 **18–20% 的 B2B 联系人每年换工作**；**任职 < 30 天 = 恭喜序列而非冷推**；预发送 LinkedIn 实时核验可把**硬退信降 40–55%** | **still_here 在职核验**（含新入职特例） |

### 6.3 明确**不**采纳的

| 项 | 原因 |
|---|---|
| **Sales Navigator 专属过滤器**（Seniority / Function / Years in Position / Spotlight） | 需付费订阅，本环境无。仅备注在 L7 付费预留位 |
| **LinkedIn 登录态抓取 / 自动化外联**（加人、发消息、Week1–4 预热序列） | 违反只读原则，**明确排除** |
| **付费 enrichment 工具**（Apollo / Hunter / Clay / Datagma API） | 仍留 L7 预留位，本次不启用 |

### 6.4 双岗设计（本次最核心的改动）

| | **L-1（新岗，找人）** | **L4（原岗，核验）** |
|---|---|---|
| 问的问题 | "这家公司里，**谁**是决策人？" | "这个人的头衔/在职状态**对不对**？" |
| LinkedIn 动作 | 公司页 JSON-LD + Employees 名单 + 4 组 query + 组织图反推 | 头衔核验 + **still_here 在职核验** + 协会名录交叉 |
| 产出 | `姓名 / 职能 / 层级 / 在职证据 / 个人页 URL` | 印证实录 + 离职风险标记 |
| 通关条件 | 拿到 ≥1 个「具名+在职+职能对口」的人 | 与 L-1 名单一致，或已修正 |
