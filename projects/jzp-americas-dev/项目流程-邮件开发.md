> **「写信的内容都交给写开发信的 agent，要有分工。」**

**每个环节只干自己的活，不越界。** 这是本项目的组织原则，不是建议。

| 环节 | 谁负责 | 只产出 | 🚫 不做什么 |
|---|---|---|---|
| **① 找客户** | 找客户 agent | **交接单**（`买家N_公司_开发信交接单.md`） | 🚫 不写正文、不碰模板、不定话术 |
| **② 写信** | **写开发信 agent** | **开发信正文**（`开发信项目/clients/开发信-*.md`） | 🚫 不找客户、不做背调、不定发送时间 |
| **③ 发送** | 发送层脚本 | 投递 + 送达记录 | 🚫 不改正文内容 |
| **④ 排程** | 排程层脚本 | 按收件人时区的北京窗口 | 🚫 不改正文内容 |
| **⑤ 回复识别** | 扫描脚本 | 意向判定 + 登记交付 | 🚫 不自动跟进 |

### ⚠️ 我必须守住的边界（2026-09-28 用户纠正）

**首封正文里的措辞、钩子、产品切片、话术 —— 全部属于环节 ②，是写开发信 agent 的活。**

我（找客户侧 / 发送侧）**不应**自作主张去改模板正文。我此前直接改
`生成草稿.py` 里的三语模板（换钩子、改主题行），**越界了**。

**我的边界：**
- ✅ 我可以：找客户 → 产交接单 → 过信息量闸门 → 判断「够不够写」
- ✅ 我可以：维护发送层/排程层脚本的**技术正确性**（闸门 bug、转义、编码）
- ✅ 我可以：校验信件是否违反**硬红线**（禁用认证 / YAWEI / 首封报交期价格）
- 🚫 我不应：替写信 agent 决定**怎么写**（换钩子、改措辞、改主题）

> **例外**：若写信 agent 尚未接入、而用户明确要求「你先把信写出来」，
> 才可由我代笔，但须在交付时注明「此为临时代笔」。

## 一、全流程

```
① 写作 agent（毅冰 Mail Group 方法论）
   产出开发信 → 开发信项目/clients/开发信-*.md
        ↓
② 发送层 发送开发信.py
   抽正文 → 接图片签名 → 红线自检 → 生成 HTML
        ↓
③ 排程层 定时发送.py
   按收件人时区算北京窗口 → 入队 → 到点投递
        ↓
④ 客户回复
        ↓
⑤ 扫描回复.py
   识别意向 → 登记 → 交付给用户
        ↓
        ⛔ 到此为止。**之后不再自动跟进。**
```

> ⚠️ **注意**：上图 ① 是「写作 agent」。而 `生成草稿.py`（模板套用式生成）
> **不是**写作 agent —— 它只是「信息量闸门 + 模板占位」的过渡工具。
> **真正的首封正文应由写作 agent 按交接单逐封写出**，不用模板 mail-merge。

## 二、🔴 发送时间铁律（用户 2026-09-27 明确）

> ### ⚠️ 关于 2026-10-02 那次「凌晨 2 点前发完」
>
> 用户 2026-10-02 明确：**「这次是例外，所以日常铁律还是要遵守」**（原话）。
> batch8 A 档 25 封因用户当天搞晚了、**主动豁免窗口**，按北京 01:03–01:42 发出，
> 结果是北美客户**在当地中午–下午**收到（ET 13:03–14:42｜CT 12:03–13:42｜
> MT 11:03–12:42｜PT 10:03–11:42），**只有美西还在上午**。
>
> 🔴 **这是一次性例外，不是先例。** 默认仍按本节的「当地工作日 08:00–10:00」排。
> 若用户再次要求夜间破例，**必须先提示这个后果**（北美大部分时区会落到当地下午）。

### 2.1 以「送达时间」为准，发送时刻用北京时间表达

> **「记住我要求的是送达时间。比如我在北京时间也就是我这边的时间，周一晚上 10 点发送，
> 送达时间也就是目标客户邮箱那边正好是周一的早上 8 点。」**

**规则**：
- **目标** = 客户**当地工作日 08:00–10:00** 送达（2 小时窗口）
- **表达** = 发送时刻用**北京时间**（用户自己这边的时间）表示
- **显示** = 两个时刻都要给出（北京发送 → 当地送达）
- **分散** = 🔴 **同一时区的信不得同一时刻发出**，要铺开在窗口内

**换算**：`北京发送时刻 = 08:00 − 客户时区偏移 + 8`

| 时区 | 发送窗口（北京·夏令） | 送达窗口（当地） | 冬令时发送（北京） |
|---|---|---|---|
| 美东 ET | **20:00–22:00** | 08:00–10:00 | 21:00–23:00 |
| 美中 CT | **21:00–23:00** | 08:00–10:00 | 22:00–24:00 |
| 美山 MT | **22:00–24:00** | 08:00–10:00 | 23:00–01:00 |
| 美西 PT | **23:00–01:00** | 08:00–10:00 | 24:00–02:00 |
| 阿拉斯加 AK | **24:00–02:00**（次日） | 08:00–10:00 | 01:00–03:00 |
| 巴西 BR | **18:00–20:00** | 08:00–10:00 | — |
| 墨西哥 MX | **21:00–23:00** | 08:00–10:00 | 22:00–24:00 |

> ✅ **用户给的例子已验证**：美山时区 北京 22:00 发送 → 当地 08:00 送达。

### 2.2 🔴 窗口内分散（用户 2026-09-27 明确）

> **「不要都是同一时间发出，正好躲开了同一时间发送多个邮箱。」**

**同一时区的信必须铺开在窗口内**，不能同一分钟批量发出——
「同一秒批量投递」是最典型的垃圾邮件特征。

实现：同一 `(时区, 窗口日)` 分组内，按 `窗口时长 ÷ 信数` 均匀分槽，
每槽取中点，再叠加 ±25% 槽宽的随机抖动。

**实测效果**（4 封美东信，2 小时窗口）：

| 信件 | 发送（北京） | 送达（当地） |
|---|---|---|
| AW-High-Voltage | 20:20 | 08:20 |
| Gresco-Utility | 20:45 | 08:45 |
| MVI-Mon-Valley | 21:11 | 09:11 |
| {{COMPANY}} | 21:51 | 09:51 |

→ 全在 08:00–10:00 内，**没有一封同一时刻**。

> ⚠️ 抖动是随机的，**每次 `--build` 会重新分配**。定稿后不要再频繁重建。

### 2.3 周末一律不发

> **「今天是周末，所有邮箱都在周一到周五送达。」**

- **周六、周日一律不发**
- ⚠️ 周末判断必须用**客户当地星期**，不能用北京星期
  （北京周六 00:00 可能是当地周五 09:00，应当可发）
- 避开发送日：当地周末 + 当地公共假日；中东客户避周五

### 2.4 🔴 发送范围：只发 A 档（用户 2026-09-29 明确）

> **「只发了 A 级的 21 个，其他的都没有发。目前都只发 A 级，B 级暂时不发。」**

| 邮箱档位 | 定义 | 处置 |
|---|---|---|
| **A** | 具名 + 已验证 / 第一方来源 | ✅ **投递** |
| **B** | 角色邮箱（`info@` / `sales@` / `contact@`）或域不可探测 | ⏸ **暂缓** |
| **B−** | catch-all 域的具名邮箱（无法验证） | ⏸ **暂缓** |
| **C+** | 弱（品牌域已死、个人邮箱） | ⏸ **暂缓** |
| **—** | 无可用邮箱 | ⛔ 改电话 |

> ⚠️ 「档」指**邮箱档位**（能否可靠送达），**不是**客户类型档
> （A 类承包商 / B 类分销商）。**一家 B 类分销商，邮箱是 A 档，照发。**

**三条依据**：
1. B 档退信率显著更高（16 个退信地址里 7 个是角色邮箱）
2. B 档「点名转交」依赖对方配合，送达不由我们控制
3. **保护发信域信誉** —— B 档退信拖累域信誉，**连带影响 A 档送达率**

**完整口径、已发 21 封明细、暂缓 22 家清单 → `发送策略-只发A档.md`**

### 2.5 ⏸ 投递前的硬闸门

```
① 只收 A 档信件进队列
② 查退信黑名单（含「整域封锁」，2026-09-29 新增）
③ 按收件人时区算窗口 + 窗口内分散
④ 当地周末 / 假日不投
```

> 🔴 **源 IP 信誉是全局阻塞项**：`223.64.2.43` 被 Spamhaus / Mimecast / Charter 多方标记，
> **不解决则大量 M365/EO 域根本无法投递**，与档位无关。

## 三、🔴 意向判定标准（用户明确）

> **「回复一定是客户表明了有意向」**

**只有明确表明意向的回复才登记交付。** 分级：

| 级别 | 信号 | 处理 |
|---|---|---|
| ✅ **明确意向** | 表示**已转/将转采购**、索要资料或报价、约谈、询问具体规格 | **登记 + 交付用户** |
| ⚠️ **需澄清** | 反问你的意图、问合作方式（还没表态） | 登记，标注需人工回复 |
| 💬 **弱意向** | 泛泛说「有需求」但无具体动作 | 登记，标注待观察 |
| ⛔ **拒联** | `remove me` / `stop` / `not interested` | 登记 + **进不再联系名单，永久排除** |
| — | 退信 / 自动回复 / 工单系统自动确认 / 营销邮件 / 自家测试件 | **不登记** |

### 判定陷阱（踩过的坑）

- **`tender` / `bom` / `submission` 这类词太泛** ——
  「我们忙着投标」不等于想采购你的东西。这些词**不能单独判定为意向**，已降级为弱意向。
- **同线程去重不能「保留最新」** ——
  意向信号常在**更早**那封里。例：{{CONTACT_NAME}} 第一封说「转给采购经理」，第二封只说
  「Sounds good」。按「最新」去重会把意向丢掉。**规则：保留意向级别最高的那封。**

## 六、用法

```bash
python3 扫描回复.py            # 扫描并登记（不发送任何东西）
python3 扫描回复.py --show     # 查看已登记记录
python3 扫描回复.py --days 7   # 只看最近 7 天
```

**产出**：
- `客户回复登记.json` —— 机器可读，供后续处理
- `客户回复登记.md` —— 人工可读，含每封的原文摘要

**重复运行是安全的**：已登记的记录会保留 `recorded_at`，不会丢历史。

## 七、边界（本脚本不做什么）

- ❌ **不代发跟进信** —— 用户明确「后面你就不需要跟进了」
- ❌ **不判断客户价值** —— 那是项目 1（找客户）的职责
- ❌ **不修改客户的原始回复** —— 只读、只登记
- ✅ 只做三件事：**识别意向 → 登记 → 交付**
