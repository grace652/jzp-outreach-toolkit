用户明确要求**环节分工**，各环节只干自己的活：

| 环节 | 负责方 | 只产出 | 不做什么 |
|---|---|---|---|
| ①找客户 | 找客户 agent | **交接单** | 不写正文、不定话术 |

① 主题以 `Re:/Fw:/回复:/转发:` 开头 ② 信件文件名含「跟进」。

### 11. 🔴 零退信的**两级处置**口径（2026-10-05 用户明确，**纪律 ≠ 铁律**）

### 13. 🔴 多定时任务并存时的隔离做法（2026-10-05 实测）

用户会同时挂多个定时任务。**每个任务用「独立队列 + 自己的 `--run` 轮询驱动」即天然零冲突。**

**本次实例**：另一会话 `a53ec1bf-…` 驱动 batch10A（28 封首封，北京 21:00–00:50），
本会话 `f9c845b2-…` 驱动 跟进1005（23 封跟进，20:30–01:48）。

| 隔离项 | 做法 |
|---|---|
| 进程 | 各自 `caffeinate -i bash /tmp/driver_<批次>.sh <队列> <日志>`，**互不 kill** |
| 锁 | 双方都用 `--run --limit 1`，**`.daemon.lock` 全程不存在** |
| 队列 | 各自独立文件，**绝不用默认 `发信队列.json`** |
| 收件人 | 必须实测**零重叠**（地址 + 域） |
| 时刻 | 全局分钟去重，**且避开对方已占用的分钟** |

**侦察命令**（动手前必跑）：
```bash
pgrep -fl "driver_"          # 看有几个驱动、各自跑哪个队列
pgrep -fl "定时发送"
ls -laT 发信队列*.json        # mtime 是「有没有人正在动它」最快的信号
cat .daemon.lock 2>/dev/null
```
⚠️ `pgrep -fl "定时发送"` **可能匹配不到** —— 若对方是「shell 轮询 + `--run`」模式，
`定时发送.py` 进程只在执行瞬间存在。**要按 `driver_` 前缀或队列文件名找。**

### 14. 🔴 `tz_of_letter()` 会判错时区 —— 排程必须用跟进表地区硬指定（2026-10-05）

实测 6 家被误判（Tryggr/Amps/Alaska Line/General Pacific/Chatham/GNS **全判成 ET**），
后果是**信在错误的当地时间送达，不报错、不退信**，只悄悄降低打开率。

⇒ **跟进队列的时区一律取 `开发信跟进表.xlsx` 的「国家/地区」列**，
   不要用 `tz_of_letter()` 自动推断。交付前验算：**每封 `scheduled_at_local` 必须是 `09:xx`**。

### 15. ⚠️ 「能发多少」受限于**信写没写**，不是只受限于名单

2026-10-05 实测：用户要求发 31 封，实际**只有 23 封有跟进信**。
积压 30 家里 **21 家只有首封信**（`开发信-XXX.md`），`开发信-跟进-XXX.md` 不存在。

⇒ **排程前必须先做「信件齐备度体检」**：
```bash
ls 开发信项目/clients/开发信-跟进*.md     # 有信集合
```
⇒ 缺信的部分**交环节②撰写**，不可用首封信或他人跟进信顶替。

### 16. 🔴🔴 「重复发送」闸门 —— 同一封信不得对同一收件人发第二次（2026-10-06 事故）

**事故**：10-05 排的 22 封跟进信，**全部是 `开发信-跟进-XXX.md` 的复用** ——
而这些文件**就是 09-28/09-30 已经投出的第 1 轮跟进信**。
实测逐字相同：`{{CONTACT_EMAIL}}`（847 字全同）、`{{CONTACT_EMAIL}}`、`{{CONTACT_EMAIL}}`、
`{{CONTACT_EMAIL}}`、`{{CONTACT_EMAIL}}`、`{{CONTACT_EMAIL}}`、
`{{CONTACT_EMAIL}}`、`{{CONTACT_EMAIL}}`。

**根因**：排程时**只检查「文件存不存在」，没检查「这封信对这个人发过没有」**。
而 `今日跟进名单-*.md` 里**明确写着**「第 2 轮需换角度，不可重复首封与第 1 轮」——
**规则只写在文档里，没落到代码**。

**影响**：送达率/域信誉**无影响**（零退信）；**客户观感负面**（6 天内同一封信发两遍）；**不可撤回**。

**已建防线**：`scripts/检查重复正文.py`（`--build` / `--check <队列>` / `--show`）
- 产出 `.workbuddy-ai/已用信件登记.json` = `{信件文件: {收件人: [发出日期]}}`
- **发前必跑 `--check <队列.json>`，有重复则 exit 1**

**两个已知边界**：
① 登记表只覆盖**有队列记录**的发送（更早的手工发送不在内）；
② `--build` **只认 `status == sent`** —— 绝不能拿 pending 项的 `scheduled_at_bj` 当「已发」
   （会把「计划」记成「事实」，闸门把自己的计划误判为重复 —— 踩过并已修）。

**推论（重要）**：`开发信-跟进-XXX.md` **是「第 N 轮」的信，不是「可复用模板」**。
第 2 轮必须**另写新文件**（命名带轮次，如 `开发信-跟进-第2轮-XXX.md`），
否则复用第 1 轮文件 = 重复发送。
