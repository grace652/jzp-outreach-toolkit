### 修复的一个真实 bug：腾讯系邮件的裸 GBK 头部

腾讯企业邮箱会把中文发件人写成**裸 GBK 字节且不做 RFC2047 编码**：
```
b'From: \xcc\xda\xd1\xb6\xc6\xf3\xd2\xb5\xd3\xca\xcf\xe4<{{CONTACT_EMAIL}}>'
         ↑ 这是 GBK 的「腾讯企业邮箱」
```
坑点：**这些字节同时也是合法 UTF-8**（解出来是希腊字母/组合符），
所以「先试 UTF-8」的常规做法会得到乱码。

**解法**：`gb18030` 与 `utf-8` 都解一遍，**按 CJK 字符数打分择优**（同分时 UTF-8 优先）。
另外不能用 `email.message_from_bytes(..., policy=default)` 取头部——它在解析阶段就把裸字节毁了，
必须先用正则从原始字节里抠出字段值再解码。
中文列对齐需按显示宽度补齐（CJK 算 2 列），否则表格错位。

## ✅ 修复：签名图片在 Gmail / macOS Mail 显示不全（2026-09-27 02:29）

用户反馈签名在 Gmail 和 macOS Mail 里显示为破图，但在企业微信里正常。

### 根因（两层，用户以为是 Mac 问题，其实不是）

**第一层：远程图片被客户端默认屏蔽。**
Gmail 和 macOS Mail 默认不加载邮件里的远程图片（隐私保护，防止发件人追踪打开率）。
企业微信能显示，因为那是腾讯自己的客户端、对自己域名放行。
**这不是 Mac 的问题，所有收件人看到的都一样。**

**第二层（更严重，用户没意识到）：图片体积严重超标。**

| 文件 | 原始尺寸 | 实际显示 | 原体积 |
|---|---|---|---|
| 01.png（Logo） | 2026×886 | **93px** | 106 KB |
| 02.jpg（认证标识条 ISO/UL/CSA/CE/cULus） | 2480×483 | **213px** | 78 KB |
| 03.jpg（产品图：单相美变/三相美变/开关柜/变电站变） | 828×364 | **264px** | 129 KB |
| 4 个社交图标 | 64×64 | 22×22 | 20 KB |
| | | **合计** | **333 KB** |

**Logo 被超采样 21 倍。** 这意味着就算改成内嵌，333 KB 也会触发
**Gmail 的 102 KB 折叠**（收件人看到「[Message clipped] 查看整个邮件」）。

### 解法：压缩 + CID 内嵌（两步都要）

**第一步：压缩**（`优化签名图片.py`）
按「显示尺寸 × 2」重采样（Retina 够用），PNG 优化 / JPEG q80：
```
333 KB → 47.2 KB（省 86%）
```

**第二步：CID 内嵌** —— 关键，这样收件人**无需点「显示图片」**图片就自动加载。

正确 MIME 结构（已实测）：
```
multipart/alternative
├── text/plain
└── multipart/related
    ├── text/html
    └── image/* × 7（各带 Content-ID: <logo> / <certs> / ...）
```
HTML 里写 `<img src="cid:logo">`，Python 用
`html_part.add_related(bytes, maintype=..., subtype=..., cid="logo")`
（`add_related` 会自动补上尖括号）。

整封邮件 **70.3 KB**，安全低于 102 KB 折叠线。

### 关键实现细节

- `msg.add_alternative(html, subtype="html")` 后，`msg.get_payload()[-1]` 才是那个 HTML part，
  要往**它**上面 `add_related`，不能往 msg 上挂
- 必须先 `set_content(纯文本)` 再 `add_alternative(HTML)`，形成 multipart/alternative，
  只有 HTML 会被部分反垃圾系统扣分
- 新增 `--no-inline` 开关，便于对比测试远程引用版

## ⏰ 定时发送能力调研（2026-09-27 03:02）

用户问：能不能像他手动发信时那样设置「定时发送」。

### 结论：**做不到服务端定时，但本机定时可以做到效果等价**

**四条通道逐一实测，全部排除服务端定时：**

| 通道 | 实测结果 |
|---|---|
| **SMTP** | ❌ 协议本身**没有定时能力**，只有"立即投递" |
| **IMAP** | ❌ 无调度扩展。实测 CAPABILITY = `IMAP4, IMAP4REV1, XLIST, MOVE, IDLE, XAPPLEPUSHSERVICE, AUTH=LOGIN, AUTH=PLAIN, NAMESPACE, CHILDREN, ID, UIDPLUS` —— 无任何 scheduling 扩展 |
| **Exchange EWS** | ❌ `ex.exmail.qq.com:443` 端口通，但 `/EWS/Exchange.asmx` 返回 **502**、`/ews/exchange.asmx` 返回 **403（Wwebsvr）** —— 端点不可用 |
| **网页版定时发送** | ⚠️ 功能**存在**（exmail.qq.com → 写邮件 → 定时发送），但是 UI 功能；用户是**扫码登录**，浏览器自动化难以复用会话 |

**补充事实**：腾讯企业邮网页版确实有定时发送（需精确到分钟）；Exchange 协议理论上支持
`DeferredDeliveryTime`，但该账号的 EWS 端点不可用。

### 可用的替代方案（效果等价）

**本机定时任务** —— 邮件先准备好，到点由脚本发出。客户收到的时间完全一样。
**唯一差别**：**用户的电脑必须开着且联网**（服务端定时则电脑关机也照发）。

可选实现：
1. **WorkBuddy 自动化任务** —— 原生，设"每天 X 点跑一次"
2. **本机 launchd** —— 不依赖任何 App
3. **脚本内定时队列** —— 按收件人时区分散发送（最适合本项目）

## 📮 DMARC/DKIM 现状复测（2026-09-27 13:23）

用户问「DMARC 是什么怎么补」。重查了 DNS，**发现比之前更严重**：

| 项 | jiezougroup.com（腾讯企业邮） | jiezoupower.com（阿里企业邮） |
|---|---|---|
| DNS 服务商 | DNSPod（`cockle.dnspod.net`） | 阿里云万网（`dns3.hichina.com`） |
| MX | `mxbiz1/mxbiz2.qq.com` | `mx1/mx2/mx3.qiye.aliyun.com` |
| SPF | `v=spf1 include:spf.mail.qq.com ~all`（**软失败**） | `v=spf1 include:spf.qiye.aliyun.com -all`（硬失败 ✅） |
| **DMARC** | ❌ **NXDOMAIN（无记录）** | ❌ **NXDOMAIN（无记录）** |
| **DKIM** | ❌ `dkim._domainkey` **无记录** | ❌ `s1024._domainkey` **无记录** |

**新发现：两个域名的 DKIM 很可能都没启用**（最常用选择器均无记录）。
这意味着 DMARC 目前**只能靠 SPF 对齐**，一旦邮件被转发就会失配。

**结论**：两个域名在邮件认证上是「裸奔」状态——SPF 半残 + 无 DKIM + 无 DMARC。
而收件箱里已经有退信，说明信誉问题已经在发生。

### 给用户的具体动作（已交付）

## 🎯 窗口放宽 + 窗口内分散（2026-09-27 15:05）

### 用户补充要求

> 「8-10点就可以的，**也要注意不要都是同一时间发出**，正好躲开了同一时间发送多个邮箱。」

**两条**：
1. 目标窗口从「当地 08:00」放宽为 **「当地 08:00–10:00」**（2 小时）
2. **同一时区的信不得同一时刻发出** —— 要铺开在窗口内

### 为什么第 2 条重要

**「同一秒/同一分钟批量投递」是最典型的垃圾邮件特征。**
原来同一时区的信窗口完全相同，`--run` 会在一批里连续发出——这是要避免的。

### 实现

同一 `(时区, 窗口日)` 分组内：
```
槽宽 = 窗口时长 ÷ 该组信数
第 i 封 = 窗口起点 + 槽宽 × (i + 0.5) + 随机抖动(±25% 槽宽)
```
常量：`SPREAD_WITHIN_WINDOW = True` / `SPREAD_JITTER = 0.25` / `WINDOW_SPAN = 2`

### 实测效果（4 封美东信，2 小时窗口）

| 信件 | 发送（北京） | 送达（当地） |
|---|---|---|
| AW-High-Voltage | 20:20 | 08:20 |
| Gresco-Utility | 20:45 | 08:45 |
| MVI-Mon-Valley | 21:11 | 09:11 |
| {{COMPANY}} | 21:51 | 09:51 |

→ 全在 08:00–10:00 内，**没有一封同一时刻**。Codale（美山，组内仅 1 封）落在 22:00 → 当地 08:00。

> ⚠️ 抖动是随机的，**每次 `--build` 会重新分配时刻**。定稿后不要频繁重建。
